#+title: Changelog

* Unreleased

** Every state past capture is logged

The default ~agile-gtd-todo-keywords~ logs each move into the =LOGBOOK=:
entering =NEXT=, =PROJ= or =EPIC= records the time, entering =WAIT= asks for
a note on what it waits on, and leaving =WAIT= records the time
(=NEXT(n!)=, =WAIT(w@/!)=, =PROJ(p!)=, =EPIC(e!)=). =TODO=, =IDEA=, =DONE=
and =KILL= are unchanged. A refile records its time too:
~org-log-refile~ is set to =time=. A configuration that sets
~agile-gtd-todo-keywords~ itself keeps its own keywords.

In an org-edna chain, closing a step still asks for its own =DONE= note and
records it on that step, by hand or through org-records-mcp with a note; the
step its =TRIGGER= moves to =NEXT= records the time of that move at once.
agile-gtd advises org-edna's =todo!= action for this while
~agile-gtd-enable-org-settings~ is on; see
[[file:docs/task-dependencies.org][Task dependencies]].

** The =%agent= and =%human= tags stay on their heading

Two tags say whose move an item is: =%agent= and =%human=, named by the new
~agile-gtd-agent-tag~ and ~agile-gtd-human-tag~. Every refresh adds both to
~org-tags-exclude-from-inheritance~, whatever ~agile-gtd-enable-org-settings~
says, so a tag on a project does not reach its children. Entries of your own
in that variable stay. The new ~agile-gtd-loop-tags~ (nil by default) names
further tags to keep on their heading the same way. A tag that leaves the
set, by renaming or by leaving that list, is inherited again after the next
refresh, unless you had excluded it yourself.

Builds of =main= before this release named the two tags =agent= and
=human=. Items tagged that way are in no loop until their tags are renamed
to =%agent= and =%human=; setting the two options to the old names instead
keeps them as they are.

** Hand an item to the agent

~agile-gtd-hand-over~ hands the open item at point, in an Org buffer or an
agenda, to the agent and asks for one note. A =TODO= or =NEXT= item moves to
=WAIT= and the note is the =WAIT= note; any other open item keeps its state
and takes a plain =LOGBOOK= note. Then =%human= comes off and =%agent= goes on.
A closed item, or a move to =WAIT= that Org refuses, is refused before
anything changes; see [[file:docs/agent-loop.org][Working with an agent]].

** Whose turn it is

Three new org-ql predicates name whose turn an item in the agent loop is:
=human-turn=, =agent-turn= and =agent-wait=, also known as
=agile-gtd-human-turn= and so on. =(agent-turn KIND)= asks for one of four
kinds of agent turn: =delegated=, =replied=, =answered= or =withdrawn=. They
read the item's own =%agent= and =%human= tags, its state, and the claim the
agent sets while it works, the property the new
~agile-gtd-agent-claim-property~ names (=AGENT_CLAIM= by default). Notes in
the =LOGBOOK= move no turn. Every item carrying a loop tag or the claim is in
exactly one turn; see [[file:docs/agent-loop.org::*Whose turn it is][Whose turn it is]].

The new =h= agenda command, /My Moves/, shows the three turns as three
blocks, by rank, and searches the files in the new ~agile-gtd-loop-files~
(nil by default) beside the agenda files, skipping a file it cannot read.
The new org-records-mcp view keys
=human-turn=, =agent-turn= and =agent-wait= ask the same of the agenda files
alone.

agile-gtd installs the =h= agenda command, and on refresh it replaces an
=org-agenda-custom-commands= entry of your own under =h=, as it does for its
other keys.

* 0.7.0

Requires org-records-mcp 0.12.0.

** The tool schema lists every view key

org-records-mcp publishes each parameter's JSON type, and the schema of
=org-view= lists every key agile-gtd generates as the values =view= takes. A
client that checks its arguments against the schema picks a key from that list
and refuses any other before the call reaches Emacs. The schema of =computed=
lists =rank= and =parent-priority=. Both are written when org-records-mcp
registers its tools, so a key a refresh adds reaches such a client once the
tools register again; see [[file:docs/org-records-mcp.org::*The keys in the tool schema][The keys in the tool schema]].

* 0.6.0

Requires org-records-mcp 0.11.0.

** Breaking change: view rows carry =rank= alone unasked

org-records-mcp answers =breadcrumbs= and =blocked= itself, so agile-gtd no
longer defines computed fields for them. A refresh adds =rank= to
~org-records-mcp-list-computed-fields~, keeping the names already there. A view
row no longer carries =parent-priority=, =blocked= or =breadcrumbs= unless the
call names them in =computed= or =fields=; a read of one node still carries
them all.

** Stuck epics count as stuck projects

An open =EPIC= with no open =PROJ=, =EPIC=, =NEXT= or =WAIT= child shows in
every Stuck Projects block and in the org-records-mcp =stuck= views, and a
sub-project or sub-epic counts as progress for its parent.

** ~org-store-link~ links by location and copies the link

An interactive ~org-store-link~ is advised by default. In a file under
~org-directory~ or ~org-roam-directory~ it links a heading by its =:ID:=,
creating one when missing; in any other file it creates a =:CUSTOM_ID:= slug
instead. It also copies the link to the kill ring as a bare link with an
absolute path, the form org-records-mcp's tools accept; ~org-stored-links~
keeps Org's own form. Calls from Lisp, including org-records-mcp's, are left
alone. Set ~agile-gtd-enable-link-ids~ or ~agile-gtd-enable-link-kill-ring~ to
nil to keep the stock behaviour; [[file:docs/storing-links.org][Storing links]] has the details.

* 0.3.0

** Breaking change: ~agile-gtd-max-priority-group~ is removed

Upgrading from a release that carried ~agile-gtd-max-priority-group~: the
defcustom and the global priority override behind it are removed, and setting
it has no effect. A single global cutoff cannot express "this view is
deliberately narrow, that view is deliberately wide", which is the whole point
of per-buffer range rotation. Its interactive role — widening the sprint
threshold on the spot — is served by ~agile-gtd-agenda-wider-range~.

~agile-gtd-sprint-prio-threshold~ is untouched and sets the =sprint= cutoff;
~agile-gtd-backlog-priority-threshold~ is likewise untouched and governs only
the =rS= SOMEDAY review command.
