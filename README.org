#+title: agile-gtd

* What this package models

=agile-gtd= packages a hybrid Agile + GTD workflow for Org mode.
It treats Org headings as planning units with explicit execution semantics:

- =EPIC -> PROJ -> NEXT/WAIT/TODO= is the normal hierarchy.
- =NEXT= and =WAIT= indicates a task currently in focus (actionable)
- =TODO= tasks are not actionable yet.
- =NEXT= and =WAIT= can also exist without a project; these are standalone next actions.
- =TODO= is captured input, not yet clarified or committed.
- Priorities =A..C= are considered in the current sprint.
- Priorities =D..E= are next in the backlog
- No assigned priority is considered between =E= and =F=
- Priorities =F..H= are the lower part of the backlog
- Priority =I= is for background tasks that do not belong to the backlog but still relevant.
- =SOMEDAY= tag removes an item from the active backlog.
- =SOMEDAY= tag plus =SCHEDULED= date turns an item into a tickler that resurfaces at the given date.
  When the tickler item resurfaces again, it shall be scheduled or assigned a priority accordingly.
- Tasks with a =DEADLINE= within 7 days are considered in the current sprint.
- Tasks with a =DEADLINE= within 14 days are considered next in the backlog.
- Tasks with a =DEADLINE= after 14 days are considered below the default priority

Headings without a TODO keyword are structural headings only.

* States

| Keyword | Meaning                                                     |
|---------+-------------------------------------------------------------|
| TODO    | Captured input that is not actionable yet.                  |
| NEXT    | Concrete next action that is actionable now.                |
| WAIT    | Open loop waiting on a person, event, or dependency.        |
| PROJ    | Multi-step outcome; should usually own NEXT/WAIT children.  |
| EPIC    | Larger body of work grouping related projects.              |
| IDEA    | Not committed work; kept out of the active execution flow.  |
| DONE    | Completed successfully.                                     |
| KILL    | Explicitly cancelled; kept for history instead of deleting. |

A project is healthy when it has at least one child in =NEXT= or =WAIT=.
A project with no such child is stuck.

* Hierarchy and execution

The workflow is built around a simple progression:

#+begin_example
EPIC
  PROJ
    NEXT
    WAIT
    TODO
#+end_example

A =NEXT= or =WAIT= without a =PROJ= ancestor is still valid and is treated as a
standalone next action.

Repeating tasks are modeled with a scheduled repeat timestamp and
=:REPEAT_TO_STATE: NEXT= so that marking them =DONE= returns them to =NEXT=.

* Priorities

Priorities run from =A= (highest) to =I= (lowest).
The default backlog priority is sorted between =E= and =F=.

| Priority    | Meaning                                   |
|-------------+-------------------------------------------|
| A..C        | Current sprint                            |
| D..E        | Near-term                                 |
| no priority | Default backlog                           |
| F..H        | Low-priority backlog                      |
| I           | background tasks, kept out of the backlog |

Priority is not only local:

- a child action inherits urgency from its parent project for sorting and grouping;
- a project priority can pull an unprioritized or lower-priority child upward in
  backlog views;
- by default, low-end priorities are treated as deep backlog and are hidden from
  normal today and sprint views.

* Deadline and Scheduled Priorities

The position on the backlog also depends on the =DEADLINE= and =SCHEDULED= dates
of a task.  Both are mapped to an effective priority using the same table:

| Days    | Effective priority |
|---------+--------------------|
| <0      | overdue            |
| =0      | today              |
| <=2     | A                  |
| <=5     | B                  |
| <=7     | C                  |
| <=11    | D                  |
| <=14    | E                  |
| <=21    | F                  |
| <=30    | G                  |
| <=60    | H                  |

=DEADLINE= affects rank for any future date (it pulls items upward as the
deadline approaches).

=SCHEDULED= only affects rank when it is today or overdue (delta ≤ 0).
A future =SCHEDULED= date does not change the rank — the item is simply not
yet due and remains sorted by its explicit priority alone.  This matches the
query behaviour: items scheduled in the future are excluded from next-action
views entirely.

* Tags

The workflow uses tags as control signals rather than decoration.

| Tag        | Meaning |
|------------+---------|
| SOMEDAY    | Deferred work, hidden from the active backlog |
| HABIT      | Recurring habit or routine |
| LASTMILE   | Final-stretch item that deserves extra visibility |
| #work      | Work item |
| #personal  | Personal item |
| @context   | GTD context such as a place, person, or tool |

Domain- or client-specific tags can be layered on top via =agile-gtd-projects=
(see [[*Projects][Projects]]).
When files use =#+filetags=, those tags classify every heading in the file.

* Deferred work

There are two important deferred states:

- =SOMEDAY=: the item is intentionally parked and should not clutter active views.
- Tickler: the item has the =SOMEDAY= tag and a future =SCHEDULED= date. It stays
  hidden until that date arrives.

Processing a tickler usually means removing =SOMEDAY=, assigning a real
priority, and optionally adding a deadline.

* Projects

Work items all carry =#work=, but different clients, teams or engagements are
told apart by a tag of their own. =agile-gtd-projects= declares them once; the
package then auto-generates a per-project agenda command, adds the tag to
=org-tag-alist=, and puts the project's file on =org-agenda-files=.

Each entry is a plist:

| Key     | Required | Description                                                         |
|---------+----------+---------------------------------------------------------------------|
| =:tag=  | yes      | Non-empty Org tag string; the project's identity                    |
| =:name= | no       | Display name; defaults to the tag                                   |
| =:file= | no       | Org file, resolved against =org-directory=; defaults to =<tag>.org= |
| =:key=  | no       | Single character for the agenda command and the tag-alist entry     |

The tag is what a project *is*. Everything that selects a project's work — its
agenda command, a tag filter typed in an agenda buffer, the clocked-time
reports of a clocking package reading the same registry — matches on the tag,
so an entry belongs to its project wherever it sits and whatever its file is
called. Changing a =:name= or moving a =:file= leaves the project's history
where it is; retagging an entry is what moves work from one project to another.
A relative =:file= is resolved against =org-directory= and nowhere else, so the
same registry means the same files whatever buffer is current when it is read.

A project without a =:key= gets no agenda keybinding and no tag-alist entry, so
it can be registered purely so that its files and its history stay in reach. A
=:key= that is not a character costs the project only those two things; the
project itself stays usable.

Keys beyond these four are tolerated and ignored, so one registry can carry
another package's extensions without this package knowing about them.

An entry that is not a plist, one whose =:tag= is not a non-empty string, and
one repeating a =:tag= an earlier entry already claims are each skipped with a
warning naming the entry and showing the shape that would have been accepted.
The warning comes once per offending entry — the registry is read on every
agenda build, and a warning repeated on each of those buries the one that
matters — and starts over when the registry is edited. Nothing raises: one
mistyped line costs its own project, never the session. Where two entries claim
one tag the first wins. Two projects sharing a file, or a display name, are
permitted.

** Configuration example

#+begin_src emacs-lisp
(setopt agile-gtd-projects
        '((:tag "acme"   :name "ACME Corp"  :key ?a)
          (:tag "globex" :name "Globex Inc" :key ?g)))
#+end_src

This generates:

- =wa= — "ACME Corp Agenda" (today + stuck projects + next actions filtered to =acme= tag)
- =wg= — "Globex Inc Agenda" (same, filtered to =globex= tag)
- Tag-alist entries: =acme= bound to =a=, =globex= bound to =g=

Project tags are expected to be applied via =#+filetags= at the file level or
inherited from a parent heading.

** Project records

=agile-gtd-project-records= returns the registry with every default already
applied: one plist per entry, carrying =:tag=, =:name=, =:file= and =:key=. All
three of tag, name and file can differ for one project, and consumers want
different ones of them — the tag matches entries, the name labels a prompt, the
file names what to scan — so the accessor keeps the defaulting rules in one
place rather than in each consumer. A declared file is carried as written,
relative names included, and expanded against =org-directory= where it is
actually used. =agile-gtd-project-files= is the file column of those same
records. Both read through the same funnel, so an entry skipped with a warning
is absent from every one of them.

** One registry for clocking too

[[https://github.com/stfl/org-clock-projects][org-clock-projects]] reads a registry in this same layout: the same =:tag=,
=:name= and =:file=, the same defaults for the two that follow from the tag,
the same tolerance for keys it does not know, and the same skip-and-warn
treatment of an entry it cannot use. =:key= is this package's own extension to
that layout — the clocking package tolerates it on input and drops it from its
own records, which is exactly what the shared contract promises an extension.
Point that package's project function at this package's accessor to keep one
registry rather than two:

#+begin_src emacs-lisp
(setq org-clock-projects-projects-function #'agile-gtd-project-records)
#+end_src

Neither package requires the other, and neither reads the other's variables.
The layout is shared by convention and held in place by a contract test in each
suite: the same declared-to-normalised table, asserted over =:tag=, =:name= and
=:file= on both sides, with =:key= the one column only this side has.

** Tag check at startup

=agile-gtd-enable= runs =agile-gtd-check-project-tags=, which warns about any
project file that does not declare its project tag. Only a file-level tag is
inherited by every entry in the file, which is what tag-based selection of
clocked time relies on; a tag worn by individual headlines leaves the rest of
the file invisible to it. The check covers the project's own file and the
archives Org resolves from =org-archive-location=, because archiving records a
subtree's inherited tags in its =ARCHIVE_ITAGS= property rather than as real
tags, so an archive needs its own =#+filetags= line.

The check never writes: Org has no built-in for setting a file tag, and the
repair is one you want to make deliberately. It is skipped in batch, where a
warning has no reader, and =M-x agile-gtd-check-project-tags= runs it on
demand.

* Agenda commands

The package installs a set of agenda commands under =org-agenda-custom-commands=:

| Key  | Name                     | Description                                     |
|------+--------------------------+-------------------------------------------------|
| =i=    | Inbox                    | Unprocessed inbox items grouped by creation date |
| =a=    | Main Agenda              | Unified daily view: all contexts, priority-grouped |
| =A=    | Agenda Weekly            | Standard week view                               |
| =l=    | Agenda Weekly with Log   | Week view with closed-item log                   |
| =r=    | Review                   | Prefix for review commands                       |
| =rc=   | Close open actions       | All active NEXT/WAIT within 30 days              |
| =rs=   | Stuck Projects           | Projects with no NEXT/WAIT child                 |
| =rt=   | Tangling TODOs           | Actions orphaned under completed ancestors       |
| =rS=   | SOMEDAY                  | Low-priority and deferred projects               |
| =p=    | Private                  | Prefix for private (non-work) commands           |
| =pp=   | Private Agenda Today     | Daily view filtered to non-work items            |
| =pb=   | Private Backlog          | Backlog filtered to non-work                     |
| =ps=   | Private Stuck Projects   | Stuck projects filtered to non-work              |
| =w=    | Work                     | Prefix for work commands                         |
| =ww=   | Work Agenda Today        | Daily view filtered to =#work= items               |
| =wb=   | Work Backlog             | Backlog filtered to =#work=                        |
| =ws=   | Work Stuck Projects      | Stuck projects filtered to =#work=                 |
| =w<key>= | /Project/ Agenda        | Per-project daily view (auto-generated)          |

The composite daily views (=a=, =pp=, =ww=, =w<key>=) show three blocks in order:
1. Agenda (today's scheduled, deadlined, and time-grid items)
2. Stuck Projects (flat list, no grouping)
3. Next Actions (grouped by ancestor priority)

All three blocks are filtered consistently: =pp= excludes =#work= items, =ww=
includes only =#work= items, and =w<key>= includes only items tagged with the
project tag. =a= shows everything unfiltered.

Interactive narrowing by tag is available in any agenda buffer via
=org-agenda-filter-by-tag= (=\= key).

* Derived concepts

The package exposes org-ql predicates for the workflow's core concepts:

| Predicate                   | Meaning |
|-----------------------------+---------|
| =agile-gtd-stuck-proj=      | project with no NEXT/WAIT child |
| =agile-gtd-standalone-next= | NEXT/WAIT without a project ancestor |
| =agile-gtd-tickler=         | deferred item with SOMEDAY + SCHEDULED |
| =agile-gtd-tickler-proj=    | project wholly parked in the tickler |
| =agile-gtd-someday=         | deferred item |
| =agile-gtd-habit=           | habit by tag or Org habit style |
| =agile-gtd-tangling=        | task left under a completed ancestor |
| =agile-gtd-work=            | any work item |
| =agile-gtd-private=         | non-work item |
| =agile-gtd-blocked=         | task with an unsatisfied org-edna BLOCKER dependency |

These predicates drive agenda commands and review views.

* Inbox and capture semantics

New input starts in the inbox as =TODO=. Clarification happens later:

- turn it into =NEXT= when it is actionable now;
- turn it into =PROJ= when it needs multiple steps;
- turn it into =WAIT= when the next move belongs to someone else;
- tag it =SOMEDAY= when it is deliberately deferred;
- keep it as =TODO= when it belongs to a =PROJ= but is not actionable yet;

- refile it to the corresponding position in the system;

The package includes capture templates for inbox items, projects, scheduled
actions, deadline-driven actions, and protocol captures.

* Task dependencies

Sequential steps inside a project can be chained using org-edna's =TRIGGER= and =BLOCKER=
properties.

The common pattern is:

#+begin_example
 * PROJ Build release
 ** NEXT Write changelog
   :PROPERTIES:
   :TRIGGER: next-sibling todo!(NEXT)
   :END:
 ** TODO Tag commit
   :PROPERTIES:
   :BLOCKER: previous-sibling
   :END:
 ** TODO Publish
   :PROPERTIES:
   :BLOCKER: previous-sibling
   :END:
#+end_example

- =TRIGGER: next-sibling todo!(NEXT)= — when this task is marked =DONE=, the next sibling
  automatically becomes =NEXT=.
- =BLOCKER: previous-sibling= — this task stays blocked until the previous sibling is =DONE=.

Blocked tasks are excluded from next-action, daily, and backlog views by =agile-gtd=.

The =agile-gtd-blocked= predicate (see [[*Derived concepts][Derived concepts]]) can be used
in custom org-ql queries to match or exclude blocked items.

Helper commands in =org-mode= buffers (=SPC m d=):

| Key   | Command                          | Effect                              |
|-------+----------------------------------+-------------------------------------|
| =d n= | =agile-gtd-trigger-next-sibling= | Set TRIGGER on current task         |
| =d b= | =agile-gtd-chain-task=           | Set TRIGGER + BLOCKER (chain step)  |

* Metadata and history

The workflow expects standard Org metadata to carry process state:

| Property          | Meaning                                   |
|-------------------+-------------------------------------------|
| =ID=              | Stable identity                           |
| =CREATED=         | Capture or creation time                  |
| =TRIGGER=         | org-edna automation for follow-up actions |
| =BLOCKER=         | org-edna dependency                       |
| =REPEAT_TO_STATE= | Repeat target, usually NEXT               |
| =Effort=          | Estimate, typically in work files         |

The LOGBOOK keeps the audit trail: state changes, clock entries, and notes.
In work contexts, the same tree can also be used with =org-clock= and effort
estimates for time tracking and reporting.

* What the package configures

=agile-gtd-enable= and =agile-gtd-refresh= install the workflow into Org by
configuring:

- TODO keywords and faces
- priority range, faces, and optional org-modern symbols
- workflow tags
- inbox and project capture templates
- agenda files and refile targets
- org-ql predicates
- agenda commands for inbox, today, review, stuck projects, and backlog views

=agile-gtd-refresh= stops there. =agile-gtd-enable= also runs the startup tag
check (see [[*Tag check at startup][Tag check at startup]]).

The exact file layout is user-configurable through variables such as
=agile-gtd-inbox-file=, =agile-gtd-todo-file=, and =agile-gtd-projects=,
but the semantics above stay the same.
