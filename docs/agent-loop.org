#+title: Working with an agent

How to hand an item to an AI agent and tell whose turn each item is, from two
tags, the state and the agent's claim. Back to the [[file:../README.org][README]].

* Whose move it is

An agent working through org-records-mcp and you share one outline. The TODO
state says what an item is; two tags say who acts on it next:

| Tag      | Whose move                                |
|----------+-------------------------------------------|
| =%agent= | The agent's: it picks the item up next.   |
| =%human= | Yours: you answer, decide or review next. |

Both tags stay on the heading that carries them. A project tagged =%human=
asks you about the project, and each of its tasks stays whoever's it was.

On every refresh, whether or not =agile-gtd-enable-org-settings= is on,
agile-gtd adds both tags to =org-tags-exclude-from-inheritance=. Your own
entries there stay, ahead of them. The names come from =agile-gtd-agent-tag=
and =agile-gtd-human-tag=, and a tag renamed there is renamed in the
exclusion on the next refresh. To keep a further tag on its heading the same
way, such as one that marks an item for another system, add it to
=agile-gtd-loop-tags=. A tag that leaves that list is inherited again after
the next refresh, unless you had excluded it yourself before agile-gtd added
it.

* Handing an item over

=agile-gtd-hand-over= hands the item at point to the agent. It works on the
heading at point in an Org buffer and on the item at point in an agenda, so
you can step through /My Moves/ and hand over as you go. It sets the state,
then takes =%human= off the item and puts =%agent= on it, and asks for one
note:

| The item is                          | Its state becomes | The note is                              |
|--------------------------------------+-------------------+------------------------------------------|
| =TODO= or =NEXT=                     | =WAIT=            | the note Org asks for on entering =WAIT= |
| =WAIT=, =PROJ=, =EPIC= or no keyword | unchanged         | a plain =LOGBOOK= note                   |
| =DONE=, =IDEA= or =KILL=             | refused           | none                                     |

When Org refuses the move to =WAIT=, for example in a file whose keywords
have no =WAIT=, the command stops before the tags change, so an item is never
left half handed over. With a region active, it still hands over the item at
point alone.

The note is what the agent needs to go on. Leave it empty when the tag says
enough: the =LOGBOOK= still records when the item changed hands. A handed-over
action reads like this:

#+begin_example
,* WAIT [#B] Draft the reply to the vendor                             :%agent:
:LOGBOOK:
- State "WAIT"       from "NEXT"       [2026-10-07 Wed 17:40] \\
  Use the figures from the last quarter.
:END:
#+end_example

Org asks for the note in its usual note buffer once the command returns.
Cancelling it there keeps the hand-over and logs nothing. The package
installs no key for the command; bind it in =org-mode-map= and
=org-agenda-mode-map= if you use it often.

Handing an item back is the agent's move: it swaps =%agent= for =%human=
through org-records-mcp and releases its claim.

* Whose turn it is

The tags say who acts next. With the state and the agent's claim they put
every item in the loop in exactly one of three turns. An item is in the loop
when it carries =%agent= or =%human= itself, or the claim. Each turn is an
org-ql predicate:

| Turn                 | Predicate      | The item                                                                          |
|----------------------+----------------+-----------------------------------------------------------------------------------|
| Your move            | =(human-turn)= | tagged =%human= and not =%agent=, unclaimed, =NEXT=, =PROJ=, =EPIC= or no keyword |
| The agent's move     | =(agent-turn)= | one of the four kinds below                                                       |
| The agent is working | =(agent-wait)= | tagged =%agent= and claimed, open, neither =TODO=, =NEXT= nor =SOMEDAY=           |

The agent's move comes in four kinds, and =(agent-turn KIND)= asks for one,
the kind written as a symbol or a string:

| Kind        | The item                                                              | It means                                                                                    |
|-------------+-----------------------------------------------------------------------+---------------------------------------------------------------------------------------------|
| =delegated= | tagged =%agent=, open, unclaimed, in any state                        | the agent picks it up                                                                       |
| =replied=   | tagged =%human= and not =%agent=, unclaimed, =WAIT= or =TODO=         | =WAIT=: you acted, over to the agent; =TODO=: not now, the agent takes the =%human= tag off |
| =answered=  | tagged =%human= and not =%agent=, unclaimed, =DONE=, =KILL= or =IDEA= | you decided; the agent records it and takes the tag off                                     |
| =withdrawn= | tagged =%agent= and closed, or claimed as described below             | you took the work back; the agent stops and releases it                                     |

A claimed item is withdrawn when it is =TODO= or =NEXT=, when it no longer
carries =%agent=, or when it is =SOMEDAY=, by its own tag or a parent's. Take
work back from the agent in whichever way fits: close the item, set it back to
=TODO= or =NEXT=, take the =%agent= tag off, or park it. The agent then stops,
releases the claim, notes what it undid and takes its tag off.

An item carrying both tags, where =%agent= went on and =%human= stayed, is the
agent's to pick up: =delegated=. A tag counts on the item itself, never by
inheritance, and a title that merely contains =:%agent:= tags nothing.

Notes in the =LOGBOOK= move no turn. Only the state, the tags and the claim
do: answering the agent takes a state change or a tag, a note alone is not
enough.

* The agent's claim

The agent sets the =AGENT_CLAIM= property when it starts on an item and
removes it when it hands the item back or finishes. Its value is the agent's
to choose; the property being there is what counts. The claim tells work the
agent is doing from work waiting for it:

#+begin_example
,* WAIT [#B] Draft the reply to the vendor                             :%agent:
:PROPERTIES:
:AGENT_CLAIM: 2026-10-07 17:45
:END:
#+end_example

The claim is read on the item itself, never inherited from a parent. Name
another property with =agile-gtd-agent-claim-property=.

* The turns in the agenda

The =h= agenda command, /My Moves/, shows the three turns as three blocks:
/Your move/, /Agent's move/ and /Agent working/. Each is grouped by rank like
the other agenda blocks. They take no range: every priority shows, and a
blocked item shows dimmed, because unblocking it may be the move. A block's
header stays when it is empty.

=h= searches the agenda files and the files in =agile-gtd-loop-files=, nil by
default. List there a file of loop items you keep out of the agenda, such as
an agent's working file; a relative name is read against =org-directory=, and
a file that does not exist or cannot be read is skipped:

#+begin_src emacs-lisp
(setopt agile-gtd-loop-files '("agentic.org"))
#+end_src

Only =h= searches them. The other agenda commands, and the view keys an
assistant asks, cover the agenda files alone.

An assistant asks for the same turns through the view keys =human-turn=,
=agent-turn= and =agent-wait=; see [[file:org-records-mcp.org][Views for AI assistants]]. Through
org-records-mcp's query tool it can ask any of the [[file:org-ql-predicates.org][org-ql predicates]],
=(agent-turn replied)= included.

An action handed to the agent is a =WAIT= like any other, so it stays in the
Next Actions blocks and the =next= view keys: the agenda lists what is open,
whoever's move it is.
